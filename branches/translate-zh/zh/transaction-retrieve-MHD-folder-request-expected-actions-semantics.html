    对请求作出决定：朝圣者的同意即为策略

    朝圣没有需要另行查找的数据共享协议。朝圣者的两条 HajjConsent 资源即为策略，每一条都约束其所指名的一方：

    • 来源方释放同意（例如 CONSENT-MYS，或本指南示例中虚构的 CONSENT-XXK）允许来源国 HIE 将 IPS 释放给 Consent.provision.actor 中指名的接收方（角色 IRCP，信息接收方），用于 Consent.provision.purpose 中的目的（TREAT），期限为 Consent.provision.period。来源国 HIE 依据其自身同意登记系统（Consent Registry）中的记录（由记录同意事务 [ITI-108] 记录）执行该同意，而非依据 IPS 中携带的副本。IPS 中的副本在签发 IPS 时签名，因此无法反映之后的撤回。
    • 东道国使用同意（CONSENT-KSA，或本指南示例中虚构的 CONSENT-XXR）约束东道国卫生部在收到 IPS 后对其的使用：如其同意文本所述，用于朝圣期间的治疗及任何后续照护。

    某个 Consent 是哪一项同意，以及向朝觐者展示的同意文本，均承载于 Consent.policyRule 中：取自 IPS.HAJJ.CONSENT CodeSystem 的代码，并将 coding.version 设置为该 CodeSystem 的版本。

    东道国 EMR 通过在 ips-pilgrimage 信任域中的信任来识别（参见消息语义中的认证说明）。仅当通行码有效、VHL 未过期、来源方释放同意在其登记系统中处于有效状态、经验证的接收方与 Consent.provision.actor 匹配、目的为治疗且请求处于 Consent.provision.period 范围内时，来源国 HIE 才释放文档。若其中任何一项无法确认，则不允许该请求。

    审计事件

    来源国 HIE 对每个请求都使用记录审计事件 [ITI-20] 记录一条审计事件，无论文档被释放还是被拒绝。VHL 第 1 卷 §1:XX.3 要求 VHL 共享方和 VHL 接收方与 ATNA 安全节点（Secure Node）或安全应用（Secure Application）组合，ITI-YY5 §2:3.YY5.5.6 规定两者都宜（SHOULD）记录文档访问请求、所用认证方法、接收方身份、VHL 文件夹 ID 和授权决定。在本指南中，来源国 HIE 记录的审计事件还应当引用：

    • 适用的策略：朝圣者的各项同意，每项以其 Consent.policyRule 代码和 CodeSystem 版本标识（例如本指南示例中的 CONSENT-XXK 和 CONSENT-XXR，版本 2.1.0）；
    • 为作出决定而从同意登记系统（Consent Registry）读取的每条 Consent 的 id 和 meta.versionId；
    • 接收方，以所用的 VHL 认证选项所识别的身份为准；
    • 使用目的（TREAT）；
    • 所释放的文档（返回的 DocumentReference），或拒绝结果。

    本指南不为朝圣使用单独的数据共享协议，因此审计事件所引用的策略就是这些同意本身。东道国 EMR 作为 ATNA 安全节点或安全应用，也宜对其接收的内容进行审计。
