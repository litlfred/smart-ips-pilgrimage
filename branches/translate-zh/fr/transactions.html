    Voici les transactions définies pour ips-pilgrimage

    record consent from wallet - request

    La transaction Record Consent Request Event est lancée par une solution de santé du pays d’origine auprès du HIE du pays d’origine. Cette transaction doit suivre la transaction IHE PCF d’enregistrement du consentement (ITI-108). Le portefeuille de santé du pays d’origine joue le rôle d’acteur Consent Record et le HIE du pays d’origine joue le rôle d’acteur Consent Registry.

    Événements déclencheurs

    • Une nouvelle directive de consentement a été enregistrée par un portefeuille de santé numérique.

      Sémantique des messages

      Sémantique des messages : requête

    • La sémantique des messages de la requête d’enregistrement du consentement utilise une ressource FHIR Consent envoyée par une requête HTTP PUT ou POST.

    • Voir https://profiles.ihe.net/ITI/PCF/ITI-108.html pour plus de détails.

    • Plus précisément,
      • Access Consent - Create (ITI-108)
      • Access Consent - Update (ITI-108)
    Sémantique des messages : réponse
    • Voir les sections Create et Update de ITI 108. Le succès ou l’échec de l’interaction de création/mise à jour est indiqué par le code de réponse HTTP (par exemple 400, 200, etc.).

      Actions attendues

    • Le consentement est stocké dans le registre des consentements. Veuillez consulter ici les déclarations de capacité de l’acteur Consent Registry

    issue VHL - request

    La transaction issue VHL Request Event est lancée par un portefeuille de santé du pays d’origine auprès du HIE du pays d’origine.

    Événements déclencheurs

    • La transaction de requête de délivrance du VHL est déclenchée lorsqu’un formulaire de configuration de la confidentialité, comprenant des paramètres de divulgation et de limite de durée, a été enregistré par un portefeuille de santé numérique.

      Sémantique des messages

      Sémantique des messages – requête
    • La sémantique des messages de la requête issue VHL doit inclure les paramètres nécessaires à la construction d’une SMART Health Link Payload, à savoir
      • indicateur de code d’accès
      • délai d’expiration
    Sémantique des messages – réponse
    • La réponse à la requête issue VHL doit inclure un CWT sérialisé sous la forme d’une image de code QR, comme spécifié dans la section Expected Actions.

      Actions attendues

      Les actions attendues du HIE du pays d’origine une fois qu’il reçoit la configuration de confidentialité sont les suivantes :

    • Le HIE du pays d’origine crée pour le pèlerin un dossier qui comprend, pour le pèlerin :
      • Document IPS en FHIR, en PDF ou les deux
      • Document IPS signé sous forme d’objet JSON JWS DSG pour chaque document inclus dans le dossier
    • Les spécifications SHL doivent être suivies pour créer un SMART Health Link qui est ensuite encapsulé dans une structure HCERT et partagé sous forme de structure CWT, selon les étapes ci-dessous :
      • Établir un emplacement qui pointe vers les références de documents dans le dossier du pèlerin selon la syntaxe suivante : “{host}/List?_id={folder_id}&_include=List:item”, où ‘folder_id’ est un identifiant unique du dossier de documents de santé du pèlerin. Cet emplacement doit être utilisé comme URL du lien de santé dans la charge utile VHL
      • Construire la charge utile SHLink
        • Minifiée
        • Encodé en Base64url
        • Préfixée par shlink:/
      • Construire le HCERT contenant le SHL généré à l’étape précédente
      • Construire la charge utile COSE comprenant le HCERT et la signer avec la clé privée au moyen du Kid
      • Construire le CWT avec l’en-tête, la charge utile et la signature
      • Sérialiser le CWT et utiliser Base64
      • Générer le code QR

    retrieve VHL folder docs - request

    La transaction Retrieve VHL folder docs Request Event est initiée par le DME du pays d’accueil auprès de la HIE du pays d’origine.

    Événements déclencheurs

    • La transaction retrieve VHL folder docs request est lancée lorsque le DME du pays d’accueil a extrait une charge utile VHL d’un code QR scanné et que le CWT déchiffré a produit une charge utile HCERT encapsulant la charge utile VHL.

      Sémantique des messages

      Sémantique des messages – requête
    • La sémantique des messages de la requête retrieve VHL folder docs doit être une requête POST telle que spécifiée par SMART Health Link Manifest Request, accompagnée du code d’accès fourni dans le corps de la requête.
    Sémantique des messages – réponse
    • La sémantique des messages doit suivre une version modifiée du message de réponse Find Document References ITI-67 et, pour une requête réussie, renvoyer un bundle FHIR qui inclut toutes les documentReference disponibles dans le dossier VHL du pèlerin. La modification de la transaction ITI-67 consiste en ce que la HIE du pays d’origine doit respecter le paramètre de recherche _include avec la valeur List:item, car l’URL générée dans la charge utile VHL est au format :

      {host}/List?_id={folder_id}&_include=List:item”

    Authentification du DME du pays d’accueil

    La requête retrieve VHL folder docs correspond à la transaction IHE Verifiable Health Link (VHL) Retrieve Manifest [ITI-YY5]. Le VHL est cité ici dans sa version 1.0.0-comment, qui est un ballot de commentaires publics, et non une publication finale ou d’implémentation à l’essai ; son texte et ses numéros de section peuvent changer. Les sections citées ci-dessous ont été lues dans la source IHE/ITI.VHL (commit 48201473), et non dans les pages publiées du ballot.

    Le VHL [ITI-YY5] nomme trois options par lesquelles le VHL Receiver (ici, le DME du pays d’accueil) s’authentifie auprès du VHL Sharer (ici, la HIE du pays d’origine) :

    • HTTP Message Signatures (RFC 9421), ITI-YY5 §2:3.YY5.4.1.3 ;
    • Option OAuth with SSRAA, utilisant le guide d’implémentation HL7 Security for Scalable Registration, Authentication, and Authorization (SSRAA), le profil HL7 FHIR d’UDAP, ITI-YY5 §2:3.YY5.4.1.4 ;
    • Option Verifiable Credential, ITI-YY5 §2:3.YY5.4.1.5.

    Ce guide montre actuellement le DME du pays d’accueil s’authentifiant auprès de la HIE du pays d’origine avec l’authentification de nœud mTLS ([ITI-19]) (voir le diagramme de séquence de la consultation pour soins non planifiés). L’authentification de nœud mTLS ne fait pas partie des trois options d’authentification VHL. Le VHL exige néanmoins un transport sécurisé : ITI-YY5 §2:3.YY5.5.1 exige la conformité au profil IHE ATNA pour la sécurité du transport, et le volume 1 du VHL, §1:XX.3, exige que le VHL Receiver et le VHL Sharer soient groupés avec un ATNA Secure Node ou Secure Application. Un canal TLS reste donc attendu, mais à lui seul il ne satisfait à aucune des options d’authentification VHL.

    Il est recommandé que le DME du pays d’accueil s’authentifie avec l’option OAuth with SSRAA. Comme l’approche mTLS actuelle, elle repose sur des certificats X.509 : la chaîne du certificat du DME du pays d’accueil remonte à une ancre acceptée dans le domaine de confiance ips-pilgrimage, de sorte que la HIE du pays d’origine identifie le destinataire par cette confiance, et non en consultant un accord distinct. Dans le cadre de cette option, la découverte et l’enregistrement SSRAA sont effectués avant la demande d’un jeton d’accès (ITI-YY5 §2:3.YY5.4.1.4). La manière dont le certificat ou la clé du DME du pays d’accueil est publié dans le domaine de confiance ips-pilgrimage n’est pas encore spécifiée par ce guide.

    Actions attendues

    • L’OCHIE destinataire vérifie si la requête VHL est valide et répond avec la documentReference sous la forme d’un bundle FHIR en JSON.
    • L’OCHIE destinataire agit en tant que VHL Document Responder et doit se conformer à la déclaration de capacités du VHL Document Responder
    Décider de la requête : les consentements du pèlerin constituent la politique

    Pour le pèlerinage, il n’existe pas d’accord de partage de données distinct à consulter. Les deux ressources HajjConsent du pèlerin constituent la politique, et chacune engage la partie qu’elle nomme :

    • Le consentement à la communication par le pays d’origine (par exemple CONSENT-MYS, ou le CONSENT-XXK fictif des exemples de ce guide) permet à la HIE du pays d’origine de communiquer l’IPS au destinataire nommé dans Consent.provision.actor (rôle IRCP, destinataire de l’information), pour la finalité indiquée dans Consent.provision.purpose (TREAT), pendant Consent.provision.period. La HIE du pays d’origine applique ce consentement à partir de son propre Consent Registry (tel qu’enregistré par la transaction Record Consent, [ITI-108]), et non à partir de la copie contenue dans l’IPS. La copie dans l’IPS est signée lors de l’émission de l’IPS ; elle ne peut donc pas faire apparaître un retrait ultérieur.
    • Le consentement à l’utilisation par le pays d’accueil (CONSENT-KSA, ou le CONSENT-XXR fictif des exemples de ce guide) régit l’utilisation de l’IPS par le ministère de la Santé du pays d’accueil après sa réception : pour le traitement pendant le pèlerinage et tout suivi des soins, comme l’indique le texte de ce consentement.

    Le type de consentement que représente un Consent, et le texte du consentement présenté au pèlerin, figurent dans Consent.policyRule : un code du CodeSystem IPS.HAJJ.CONSENT, avec coding.version défini sur la version du CodeSystem.

    Le DME du pays d’accueil est identifié par la confiance dans le domaine de confiance ips-pilgrimage (voir la note sur l’authentification dans la sémantique des messages). La HIE du pays d’origine ne communique les documents que lorsque le code d’accès est valide, que le VHL n’a pas expiré, que le consentement à la communication par le pays d’origine est actif dans son registre, que le destinataire vérifié correspond à Consent.provision.actor, que la finalité est le traitement et que la requête s’inscrit dans Consent.provision.period. Si l’une de ces conditions ne peut être établie, la requête n’est pas autorisée.

    Événement d’audit

    La HIE du pays d’origine enregistre un événement d’audit avec Record Audit Event [ITI-20] pour chaque requête, que les documents soient communiqués ou refusés. Le volume 1 du VHL, §1:XX.3, exige que le VHL Sharer et le VHL Receiver soient groupés avec un ATNA Secure Node ou Secure Application, et ITI-YY5 §2:3.YY5.5.6 indique que tous deux DEVRAIENT journaliser les requêtes d’accès aux documents, la méthode d’authentification utilisée, l’identité du destinataire, l’identifiant du dossier VHL et la décision d’autorisation. Dans ce guide, l’événement d’audit enregistré par la HIE du pays d’origine doit également citer :

    • la politique applicable : les consentements du pèlerin, chacun par son code Consent.policyRule et la version du CodeSystem (par exemple CONSENT-XXK et CONSENT-XXR dans les exemples de ce guide, version 2.1.0) ;
    • les id et meta.versionId de chaque Consent lus dans le Consent Registry pour la décision ;
    • le destinataire, tel qu’identifié par l’option d’authentification VHL utilisée ;
    • la finalité d’utilisation (TREAT) ;
    • les documents communiqués (les DocumentReferences renvoyées), ou le refus.

    Ce guide n’utilise pas d’accord de partage de données distinct pour le pèlerinage ; les consentements eux-mêmes constituent donc la politique que cite l’événement d’audit. Le DME du pays d’accueil, en tant qu’ATNA Secure Node ou Secure Application, devrait également auditer ce qu’il reçoit.

    retrieve IPS - request

    La transaction Retrieve IPS Request Event est initiée par le DME du pays d’accueil auprès du HIE du pays d’origine.

    Événements déclencheurs

    • La transaction de requête de récupération de l’IPS est déclenchée lorsque le DME du pays d’accueil a extrait le bundle de DocumentReference du dossier VHL et demande alors la récupération de l’IPS au format JSON.

      Sémantique des messages

      Sémantique des messages : requête
    • La sémantique des messages de la requête de récupération de l’IPS doit être une requête GET portant sur l’IPS au format JSON.
      • Le DME du pays d’accueil doit agir en tant que Document Consumer et suivre ITI-68.
    Sémantique des messages : réponse
    • La sémantique des messages de la réponse à la requête de récupération de l’IPS doit envoyer l’IPS sous forme de fichier JSON.

      Actions attendues

    • Le destinataire OCHIE répond avec l’IPS au format JSON.
